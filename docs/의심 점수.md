# 의심 점수: 버튼 하나로 몰카와 부정행위 카메라를 함께 찾기

2026-11-16 정리. 몰카(숙소·화장실 등)와 시험 부정행위 카메라를 **모드를 나누지 않고** 한 흐름으로 찾는 방법이다. 지금의 네 단계([네 단계 검토](네%20단계%20검토.md))를 그대로 두고, 탐지와 판별 사이를 '의심 점수'로 바꾼다. 점수 매기기와 감시는 펌웨어에 넣었다(11절). 숫자는 시작값이고, 실물 실험(10절)으로 고친다.

대상은 **Wi-Fi로 내보내는** 부정행위 장비다. LTE·블루투스로 내보내는 장비는 잡지 못한다(8절). 발표에서도 "시험 부정행위를 잡는다"가 아니라 "Wi-Fi로 내보내는 부정행위 카메라를 잡는다"로 말한다.

## 1. 한 줄로

- 사용자는 **"점검 시작" 버튼 하나**만 누른다. 장소를 고르지 않는다. 이 문서에서 '몰카'는 숨겨서 찍어 보내는 카메라(숙소·화장실·탈의실 등), '시험장 카메라'는 부정행위용 카메라다.
- 수신기는 기기마다 **증거를 쌓아 의심 점수**를 매긴다. 환경이 다르면 쌓이는 증거가 달라서, 같은 흐름이 상황마다 다르게 움직인다.
- 많이 올려 보내는 기기가 **둘 이상**이라 애매할 때만 "걸어 주세요"를 요청한다. 하나뿐이면 걷지 않고 바로 잰다. 시험장처럼 걸을 수 없는 곳에서도 건너뛴다.
- 점수를 매기는 규칙은 처음엔 손으로 정하고, 실험 자료가 쌓이면 **AI가 배운다**.

## 2. 왜 모드를 나누지 않나

처음에는 '몰카 점검 모드'와 '시험장 감시 모드'를 따로 두는 안을 생각했다. 두 경우의 차이는 아래 넷뿐이었다.

| 차이 | 몰카 (숙소·화장실 등) | 시험장 |
|---|---|---|
| 정상 기기 | 많다 (공유기, TV, 폰) | 없어야 한다 (폰 수거) |
| 확정 방법 | 걷기에 반응하는지 | 있는 것 자체가 의심 |
| 점검 시간 | 들어가서 몇 분 | 시험 내내 |
| 결과를 읽는 법 | 방향과 추정 구간 | 같은 구간을 좌석으로 읽음 |

넷 다 '모드'가 아니라 **증거와 시간의 차이**다. 그래서 모드를 없애고 아래 한 흐름으로 합친다.

- 사용자가 상황을 판단하지 않아도 된다. 원룸, 업소, 회의실처럼 두 모드 어디에도 딱 맞지 않는 곳에서도 그대로 쓴다.
- 코드가 갈라지지 않는다. 시나리오가 늘어도 증거 하나를 더하면 된다.
- 논문에서도 "특정 장소용"이 아니라 "환경에 따라 증거를 조합하는 방법"이라고 쓸 수 있다.

## 3. 흐름

| 순서 | 하는 일 | 지금 설계와 다른 점 |
|---|---|---|
| ① 기준선 | 시작할 때 둘레 기기 목록을 저장한다. 사용자는 자기 폰 같은 것을 "내 기기"로 표시할 수 있다. **시험장은 응시자가 들어오기 전에 시작한다**: 그러면 켠 채로 들고 온 장비도 '새로 나타남'이 된다 | 새로 생김 |
| ② 감시 | 사용자가 멈출 때까지 계속 듣는다. 몰카 점검은 몇 분, 시험장은 시험 내내 | 지금은 한 번 훑고 끝 |
| ③ 의심 점수 | 기기마다 증거를 쌓아 점수와 이유를 낸다 (4절) | 지금은 "초당 30개 이상, 평균 300바이트 이상"이면 후보. 이 규칙은 증거 하나로 들어간다 |
| ④ 확인 요청 | 많이 올려 보내는 '의심 기기'가 둘 이상이면 그때만 "55초 걸어 주세요". 하나뿐이면 '유일한 업로더' 증거로 바로 넘어간다 | 지금은 항상 55초 걷기 |
| ⑤ 위치 측정 | 점수가 높은 기기부터 잰다. 그 기기가 붙은 핫스팟·라우터도 같이 잰다 (5절) | 허브를 같이 재는 것이 새로 생김 |
| ⑥ 표시 | 점수, 이유, 추정 구간을 폰에 보여 준다 | 이유가 같이 뜸 |

## 4. 증거와 시작 점수

| 증거 | 뜻 | 시작 점수 | 누가 보나 |
|---|---|---|---|
| 기준선 뒤에 새로 나타남 | 점검을 시작한 뒤 켜진 기기 | +2 | 탐지 동글 |
| 올려 보내는 양이 많음 | 초당 30개 이상, 평균 300바이트 이상 (지금 탐지 규칙) | +2 | 탐지 동글 |
| 송출 패턴 | 꾸준히 보냄 / 일정 주기로 몰아서 보냄 / 가끔 터짐 | +1~+2 | 탐지 동글, 내장 Wi-Fi(CSI 수) |
| 걷기에 반응 | 판별 단계의 결과 (1.12배 이상, 3번 중 2번) | +3 | 탐지 동글 또는 내장 Wi-Fi |
| 유일한 업로더 | 내 기기를 빼면 많이 올려 보내는 기기가 이것 하나뿐이고 멀지 않음 | +1 | 탐지 동글. 정상 업로더가 없는 방이면 걷지 않아도 '카메라'까지 오른다 |
| 개인 핫스팟·숨긴 네트워크에 붙음 | 공유기가 아닌 곳에 연결 (핫스팟 주소가 임의 주소이거나 이름이 폰 계열) | +1, **그곳으로 데이터를 올리기까지 하면 +2** | 탐지 동글. 정상 기기는 보통 건물·숙소 공유기에 붙는다 |
| 여러 번 몰아서 보냄 | 핫스팟 같은 곳에 붙은 기기가 몰아서 보내기를 3번 넘게 함 (사진을 찍을 때마다) | +1 | 탐지 동글. 공유기에 붙은 노트북·폰도 늘 몰아서 보내므로 핫스팟에 붙은 기기에만 준다 |
| 기기가 붙은 핫스팟 | 개인 핫스팟처럼 보이는 Wi-Fi에 기기가 붙어 있음 | +1 (핫스팟에) | 탐지 동글. 카메라가 아직 아무것도 안 올려도 핫스팟은 '의심 기기'가 된다 |
| 카메라 같은 이름·제조사 | SSID 패턴(예: 카메라 앱 계열), MAC 앞 6자리 | +1 | 탐지 동글. **MAC이 랜덤이면 이 증거는 빠진다** (실험한 카메라가 랜덤 MAC이었다) |
| 가까움 | 신호가 셈 (−75dBm 아래면 다른 방일 수 있음) | +1 / −1 | 탐지 동글 |
| 내 기기로 표시됨 | 사용자가 표시함 | 제외 | 사용자 |

- 결과 화면에는 점수와 **이유**가 같이 나온다. 예: "새로 나타남 + 올려 보내는 양 많음 + 걷기에 반응 → 카메라 가능성 높음".
- 점수 구간(시작값): 5 이상 = 카메라, 3~4 = 의심 기기, 2 이하 = 무시. 실험으로 고친다.
- 기준선에 이미 들어간 장비(처음부터 켜고 온 시험장 카메라)는 '새로 나타남'이 없다. 그래서 위의 핫스팟·버스트 증거만으로도 오르게 했다: 누르기 전에는 핫스팟이 '의심'(3점), 몇 번 누른 뒤에는 카메라가 '카메라'(5점, `tests/test_score.py` 의 `exam_on_from_start`).
- 걷기에 반응하지 않아도 점수가 3~4면 '의심 기기'로 두고 위치를 잰다. 지금의 판별 규칙과 같은 생각이다.

## 5. 허브 같이 찾기

사진이나 영상을 밖으로 보내려면 카메라 옆에 **폰 핫스팟이나 작은 라우터**가 있어야 한다 (자기 Wi-Fi를 만드는 카메라는 스스로가 허브다).

- 탐지 동글은 데이터 프레임의 주소 쌍(보내는 쪽, 받는 쪽)을 본다. 그래서 **어느 카메라가 어느 허브에 붙었는지** 짝을 지을 수 있다.
- 허브는 AP라서 절전하지 않고 비콘을 계속 보낸다. **카메라가 조용할 때도 허브는 보인다.**
- 시험장에서는 허브와 카메라가 같은 응시자 몸에 있을 가능성이 크다. 허브를 찾으면 그 응시자를 좁힐 수 있다.
- AP는 늘 깨어 있어서 응답 유도(ACK, [비콘 검토](비콘%20검토.md) 5절 B)가 가장 잘 먹히는 대상이다. 절전 중인 카메라도 프레임을 계속 받으면 잠들지 못하고 답한다는 연구가 있다 (Polite WiFi, 11절).
- **ACK에는 보낸 쪽 주소가 없다.** 받는 쪽 주소만 있어서 nexmon 의 주소 필터로 거를 수 없다. 보낸 시각 바로 뒤에 온 것(순서)과 서브캐리어 세기 모양으로 누구 것인지 가린다 (`host/ack_check.py`). 또 프레임을 OFDM 속도(6Mbps 이상)로 보내야 ACK도 OFDM으로 와서 CSI가 나온다.
- **주의: 허브가 보인다고 허브의 위치를 잴 수 있는 것은 아니다.** 허브의 비컨은 2.4GHz에서 보통 1Mbps 11b로 나가서 nexmon이 CSI를 뽑지 못할 가능성이 크다([비콘 검토](비콘%20검토.md) 3절). 카메라가 사진을 올리는 동안에는 허브가 카메라에게 돌려보내는 데이터 프레임(OFDM)이 있어서 CSI가 나온다. 그래서 **카메라가 보내는 때에 카메라와 허브를 같이 잰다.** 카메라가 조용할 때 허브의 위치를 재는 것은 응답 유도(S4)가 될 때만 가능하다.

## 6. 상황마다 어떻게 돌아가나

같은 버튼, 같은 코드다. 환경이 달라서 결과가 달라진다.

| 상황 | 쌓이는 증거 | 확인 요청 | 결과 |
|---|---|---|---|
| 몰카, 다른 업로더 있음 (영상 통화 중인 폰 등) | 올려 보내는 양 많음, 꾸준히 보냄. 폰도 비슷하게 뜬다 | 한다. 걷기에 반응하는 쪽이 카메라 | 방향과 추정 구간 |
| 몰카, 다른 업로더 없음 | 올려 보내는 양 많음, 꾸준히 보냄, 유일한 업로더 | 안 한다 | 방향과 추정 구간 |
| 시험장 (몇 초마다 찍는 카메라) | 새로 나타남, 일정 주기로 몰아서 보냄, 핫스팟 | 안 한다. 기기 자체가 거의 없다 | 같은 추정 구간을 좌석 두세 개의 구역으로 읽고, 감독관이 눈으로 확인한다 |
| 시험장 (버튼을 누를 때만 찍는 카메라) | 새로 나타남, 핫스팟. 누를 때마다 터지는 전송 | 안 한다 | 허브로 먼저 찾고, 위치는 응답 유도로 잰다 (S4) |
| 시험장 (처음부터 켜고 들어와 마음대로 찍는 카메라) | 새로 나타남 없음. 핫스팟에 붙어 올림, 여러 번 몰아서 보냄, 기기가 붙은 핫스팟 | 안 한다 | 누르기 전엔 핫스팟이 '의심', 몇 번 누른 뒤 카메라가 '카메라'. 위치는 응답 유도로 |
| 원룸·업소·회의실 | 상황에 따라 위 둘 사이 | 애매하면 한다 | 방향과 추정 구간 |

**좌석까지는 어렵다.** 강의실에서는 수신기에서 좌석까지 5~9m 다. 방향이 10° 틀리면 1~1.5m, 좌석 한두 칸이 어긋난다. 방 시뮬레이션의 방향 오차는 골 찾기로 가운데 값 25° 안팎이었고, 곡선 전체를 맞춰 읽으면 크게 줄지만 실물 기준 곡선으로는 아직 확인하지 못했다. 그래서 목표는 '좌석 두세 개 구역'이고, 시험 쉬는 때에 수신기를 3~4곳으로 옮겨 재면 더 좁혀진다.

**위치 측정 쪽 영향.** 꾸준히 보내는 카메라는 지금 방식 그대로 된다. 몇 초마다 몰아서 보내거나 가끔만 보내는 카메라는 판이 골을 지날 때 패킷이 없을 수 있다. 그래서 각도마다 다음 전송이 올 때까지 기다리거나(2단계 집중 스캔으로 기다릴 각도를 줄임), 응답 유도로 패킷을 만든다. 이것이 DiffLoc+가 한계로 적은 "초당 30~50개의 안정적인 패킷 필요"를 넘는 부분이고, 논문 기여로 이어진다.

## 7. AI를 쓰는 곳

처음에는 4절의 손으로 정한 점수로 시작한다. 자료가 쌓이면 아래 순서로 AI로 바꾼다.

| 순서 | 무엇 | 입력 | 출력 | 자료 |
|---|---|---|---|---|
| 1 | 증거 가중치 배우기 | 4절의 증거들 (참/거짓, 크기) | 카메라일 확률 | 우리가 라벨을 붙인 점검 기록. 처음엔 시뮬레이션으로 만든 가짜 기록을 섞는다 (판별 검사에 쓴 가짜 자료 생성기를 넓힘) |
| 2 | 송출 패턴 알아보기 | 기기별 0.5초 칸의 개수·바이트 수 시계열 | 꾸준함 / 주기 / 터짐 / 카메라 아님 | 카메라 여러 대와 폰·노트북·스피커의 실제 기록 |
| 3 | 기준선과 다른 것 찾기 | 시험장에서 시작 전과 지금의 둘레 | 이상한 기기 | 빈 강의실·시험장 기록 |

- 1번은 로지스틱 회귀 같은 작은 모델로 충분하다. 왜 그렇게 판단했는지 설명하기 쉬워서 결과 화면의 '이유'를 그대로 살릴 수 있다.
- 2번은 작은 1D CNN이나 GRU 정도. 파이에서 돌릴 수 있는 크기로 한다.
- 위치 측정의 '신호 판독 AI'(재측정 없이 맞히기)와는 따로다. 이 문서의 AI는 "무엇이 카메라인가"를, 그쪽은 "어디에 있나"를 맡는다.
- 평가는 몰카 점검에서는 '카메라를 놓치는 비율과 잘못 잡는 비율', 시험장에서는 '한 시간에 잘못 울리는 횟수'로 본다.

## 8. 못 잡는 것 (범위 밖)

제목이 "Wi-Fi 송출형 초소형 카메라 탐지 및 위치 추정 시스템"이므로 아래는 대상이 아니다.

- 버튼을 누를 때만 Wi-Fi를 켜는 카메라 (평소에 아무것도 안 나감)
- 블루투스로 폰에 붙고, 폰이 LTE로 내보내는 경우
- 카메라 자체에 LTE가 있는 경우
- 녹화만 하는 SD 저장형 카메라 (렌즈 반사 점검을 같이 쓰라고 안내)
- **5GHz 로 붙은 장비**: 지금 탐지 동글(RT5370, MT7601U, AR9271)은 2.4GHz 만 듣는다. 초소형 카메라는 거의 2.4GHz 전용이라 카메라가 붙는 허브도 2.4GHz 를 열지만, 5GHz 카메라가 나오면 놓친다. 듀얼밴드 동글(MT7612U)로 바꾸면 풀린다

실제 사례도 이 범위를 생각하고 읽는다. 세무사 사건은 전송 방식이 공개되지 않았고, TOPIK 사건은 이어폰과 송수신기라 LTE·블루투스였을 가능성이 크다. Wi-Fi가 확인된 것은 튀르키예 사건이다(11절의 바탕 자료).

### 실험 방법

**공통 준비**
- 수신기: 탐지 동글을 꽂는다 (점검에는 꼭 필요하다). 폰으로 수신기 화면을 연다.
- 카메라 두 가지: MISUKO(앱 '구목지련', 2.4GHz) 와 '가짜 카메라'. 가짜 카메라는 노트북이다: 폰 핫스팟에 붙이고 사진 파일을 일정 간격으로 올리는 스크립트를 돌린다. 주기를 마음대로 바꿀 수 있어 S3에 쓴다.
- 폰 핫스팟은 **2.4GHz** 로 연다 (아이폰: '호환성 최대화' 켜기, 갤럭시: 모바일 핫스팟 → 대역 2.4GHz). 탐지 동글이 2.4GHz 만 듣는다.
- 정답 주소를 적어 둔다: 카메라·핫스팟·노트북·내 폰의 MAC. 카메라는 앱에서 못 보면 점검 화면에서 켜는 순간 '새로 나타남'으로 뜨는 주소를 적는다.
- 기록: 수신기의 `~/detecam/data/watch_*.jsonl` 을 노트북으로 가져와 `python3 firmware/host/watch_report.py 기록.jsonl --camera <카메라> --hub <핫스팟>` 으로 숫자를 낸다. 실험마다 시각과 한 일을 손으로도 적는다 (예: '14:05:30 카메라 켬').
- 같은 실험을 세 번 한다. 한 번만 하면 운인지 모른다.

**S1 몰카 점검처럼 꾸민 방 (약 30분)**
1. 방에 카메라(앱으로 실시간 보기 켬), 영상 통화 중인 폰, 유튜브를 트는 노트북을 같은 공유기에 붙여 둔다. 모두 먼저 켜 둔다: 몰카는 점검 전부터 켜져 있다.
2. 수신기 화면에서 '점검 시작' (걷기 확인 켠 채로). 첫 바퀴 30초는 기준선이다.
3. 애매한 기기가 둘 넘으면 화면이 '걸으며 확인'을 시킨다. 시키는 대로 걷고 멈춘다.
4. 5분 뒤 '멈춤'. 카메라·폰·노트북의 등급과 이유를 적는다.
5. 바꿔 보기: 영상 통화 폰을 카메라 바로 옆에 둔다 / 카메라 실시간 보기를 끄고 대기 상태로 둔다 / **폰과 노트북을 끄고 카메라만 남긴다** (걷기 요청 없이 '유일한 업로더'로 오르는지).

**S2 빈 강의실 (약 30분)**
1. 강의실 앞에 수신기를 둔다. 아무도 없는 채로 '점검 시작', '걸어서 확인할 수 없는 곳'에 표시.
2. 3분 기다린다 (기준선과 조용한 상태).
3. 좌석 하나(앞에서 셋째 줄 등, 정답 좌석을 적는다)에 폰 핫스팟을 켜고, 카메라를 그 핫스팟에 붙여 실시간 보기를 켠다.
4. '카메라 가능성 높음'으로 오를 때까지 걸린 시간을 적는다. 10분 뒤 멈춤.
5. 그 기기를 '이 기기 위치 재기'로 고르고 3~4곳에서 잰다. 추정 구간이 정답 좌석을 덮는지, 구간이 좌석 몇 개 크기인지 적는다.
6. 바꿔 보기: 정답 좌석을 앞·가운데·뒤로 / 핫스팟만 켜고 카메라는 끈 채로 (버튼 카메라의 평소 모습) / **핫스팟과 카메라를 켠 채로 두고 '점검 시작'** (처음부터 켜고 들어온 경우: 기준선에 들어간 뒤 몇 번 찍었을 때 오르는지).

**S3 몇 초마다 / 누를 때만 (약 1시간)**
1. S2 와 같게 하되 카메라 대신 노트북 '가짜 카메라'를 핫스팟에 붙인다.
2. 3초마다, 10초마다, 30초마다 사진(약 200KB)을 올리게 하며 각각 10분씩 점검한다. 이유에 '일정 주기로 몰아서 보냄 (약 N초마다)'가 맞게 뜨는지 본다.
3. 누를 때만: 손으로 1~2분에 한 번 올린다. '가끔 터지듯 보냄'이나 핫스팟만으로 잡히는지 본다.
4. 주기마다 지금 재기(판 회전)를 한 자리에서 3번 하고, 한 바퀴에 그 기기의 CSI 가 몇 개 들어오는지, 골이 보이는지 적는다. 여기서 '각도마다 멈추고 기다리는 재기'가 필요한지 정한다.

**S4 응답 유도 (파이와 카메라만으로, 약 2시간)**

필요한 것: 파이(지금처럼 노트북에 랜선), 카메라(MISUKO), 폰(핫스팟과 카메라 앱), 노트북. 노트북은 랜선으로는 파이에, Wi-Fi로는 폰 핫스팟에 붙인다.
파이의 무선칩 하나는 CSI를 듣는 데 쓰므로 프레임을 보낼 수 없다. 그래서 여기서는 **'남이 보낸 프레임에 대한 응답'** 을 이용한다: 노트북이 핫스팟을 거쳐 카메라에게 핑을 보내면, 핫스팟이 카메라에게 프레임을 보내고 카메라는 ACK와 핑 답장으로 답한다. 연결 안 된 쪽에서 보내는 진짜 응답 유도(S4-4)와 다른 점은 '누가 보냈나'뿐이고, 응답 프레임의 CSI로 위치를 잴 수 있는지는 이걸로 확인된다.

준비
- 폰 핫스팟을 2.4GHz로 열고 카메라를 붙인다. 채널은 노트북에서 `nmcli -f SSID,CHAN,BSSID dev wifi` 로 본다. 정답 주소: 카메라(전에 본 `c6:26:06:68:85:83`, 바뀌었으면 앱이나 점검 화면에서), 핫스팟의 BSSID.
- 카메라의 IP: 노트북에서 `ip neigh` 나 폰 핫스팟 화면의 '연결된 기기'.
- 수집은 늘 하던 `tools/manual_scan.py` 를 **`--mac` 없이** 쓴다 (주소 필터를 끄면 ACK 도 들어온다). 분석은 `python3 firmware/host/ack_check.py 폴더 --cam <카메라> --peer <핫스팟 BSSID>`.

S4-1 응답 프레임에서 CSI가 나오나 (10분)
1. 카메라와 파이를 1m 떨어뜨리고, 폰 앱으로 실시간 보기를 켠다. 폰은 다른 방이나 3m 넘게 떨어뜨린다 (세기로도 둘을 가르려고).
2. `manual_scan.py --ch <채널>` 을 돌리고 기준선 10초가 끝나면 `q`. 같은 것을 `--mac <카메라>` 로 한 번 더 한다.
3. `ack_check.py` 로 본다: ACK(주소 없음)가 몇 개 들어왔나, 순서·모양으로 가린 결과가 얼마나 맞나, 카메라 ACK의 세기가 카메라 데이터와 비슷한가. 필터를 켠 기록에는 ACK 가 없어야 한다.
4. ACK 가 0개면 바로 결론 내지 않고 조건을 바꿔 다시 본다: 실시간 보기 끄고 핑만 / 채널 바꾸기 / 1m → 30cm. 그래도 0개면 'BlockAck(보낸 주소 있음)만 쓸 수 있다'로 정리한다.

S4-2 조용한 카메라에서 응답을 끌어낼 수 있나 (20분)
1. 앱을 꺼서 카메라를 대기 상태로 둔다 (연결은 유지).
2. 노트북에서 카메라에게 핑을 30초씩, 빠르기를 바꿔 보낸다: `ping -i 0.2`, `sudo ping -i 0.05`, `sudo ping -i 0.02`. 핑 결과(잃은 비율, 걸린 시간)를 저장한다. 그동안 파이는 필터 없이 기록한다.
3. 빠르기마다 카메라의 응답 CSI(핑 답장 데이터 + ACK)가 초당 몇 개인지 본다. 대기 상태에서 걸린 시간이 100ms 넘게 들쭉날쭉하면 절전 중이라는 뜻이다: 이때 핑을 계속 보내면 깨어 있게 되는지(걸린 시간이 줄어드는지)를 본다.
4. 기준: 초당 20개 넘게. 넘는 빠르기를 S4-3에 쓴다.

S4-3 응답만으로 골이 같은 곳에 생기나 (1시간)
1. 11/15 손 측정과 같은 방식(판을 막대로 옮기고 몸은 반대편, `--truth` 로 실제 방향)으로, 카메라는 대기 상태, 노트북은 S4-2에서 고른 빠르기로 핑을 계속 보낸다.
2. 1m에서 두 방향, 그다음 3m에서 두 방향. 방향마다 한 번은 실시간 보기를 켜고(데이터로 재기) 한 번은 끄고(응답으로 재기) 잰다.
3. `ack_check.py 폴더 --cam … --peer …` 가 '카메라 데이터', '카메라 응답(순서로)', '카메라 응답(모양으로)' 의 골 가운데와 실제와의 오차를 낸다.
4. 기준: 응답의 골이 데이터의 골과 10° 안, 실제와의 오차는 관문 2 기준(30°) 안.
5. 3m 결과는 관문 2 의 거리 조건을 미리 본 것으로도 쓴다.

S4-4 연결 안 된 쪽에서 보내는 응답 유도 (나중에, 동글이 있을 때)
- 모니터 모드로 보낼 수 있는 동글(교수님께 받은 탐지 동글 등)로, 카메라와 핫스팟 주소에 OFDM 속도의 null 프레임을 보내고 ACK가 몇 % 오는지, 계속 보내면 대기 중인 카메라가 깨어 있는지 본다. 판을 돌려 S4-3과 같은 결과가 나오면 '조용한 카메라·허브의 위치'가 끝난다.
- 남의 기기에 보내는 일이라 **우리 장비로만** 하고, 실제 쓰임은 지도교수님과 전파법을 검토한 뒤 정한다. 펌웨어에는 그때 넣는다.

**S5 아무것도 없는 강의실 (1시간 이상)**
1. 카메라와 핫스팟 없이, 사람들이 오가는 평소 강의실(수업이 없는 때, 복도에 사람 있음)에서 '점검 시작', 걷기 확인 끔.
2. 한 시간 그대로 둔다. 그동안 들어온 사람의 폰·노트북이 잘못 울리는지가 핵심이다: 실제 시험장은 폰을 걷지만 스마트워치, 감독관 폰, 옆 강의실 기기가 있다.
3. `watch_report.py` 의 '잘못 울림'과 그 이유를 본다. 자주 울리게 만든 증거의 점수를 낮추고 같은 기록으로 다시 돌려 견준다 (규칙을 고칠 때마다 다시 실험하지 않아도 된다).

**결과를 어디에 쓰나**
- 4절의 점수와 구간(5 / 3)을 S1·S2·S5 로 고친다. 잡는 것(S1·S2)과 잘못 울림(S5)의 맞바꿈을 표로 남긴다.
- 기록 파일은 7절의 AI(증거 가중치, 송출 패턴)의 학습 자료가 된다. 실험마다 정답 주소를 같이 남긴다.
